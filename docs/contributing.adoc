= Contribute to the platform

[#verify-native-windows]
== Run the examples on Windows

Use this path to work on Win32 behaviour and test the app examples. To
write your own app, start at xref:apps.adoc#get-started[Create and package a starter app].

Install the x64 Windows builds of
https://github.com/lukewilliamboswell/roc-blueprint/releases/tag/0.13.0[Blueprint 0.13.0]
and https://github.com/roc-lang/nightlies/releases[Roc]. Put
`blueprint.exe` and `roc.exe` on your PowerShell path. Use a platform bundle
built from this checkout. In a scratch directory, run `roc unbundle` on
its raw `HASH.tar.zst` archive and copy the extracted `targets/` folder
into `platform/` in your checkout.

Run the suite from the repository root on Windows x64.

[source,powershell]
----
blueprint run test-native -- --target x64mingw
----

On Windows on Arm, run the x64 Blueprint and Roc binaries under Windows
emulation and pass `--target arm64mingw` to test native ARM64 executables.
The task runs Roc expects and the app's specs where present.

For host changes on Windows, install Rustup and Zig 0.17.1. Run
`blueprint run build` to rebuild the local link inputs and examples.
`blueprint run check` also links and runs Cargo tests with your native
Rust toolchain. Install the linker for that toolchain if Cargo needs it.
Run `blueprint run bundle` from a checkout with spaces in its path as part
of the first native contributor verification.

To develop one example interactively, open PowerShell at the repository root.

[source,powershell]
----
Set-Location examples/starter
roc ../../cli/windows.roc -- run --target x64mingw
----

When verifying a release, use the same staged bundle on each architecture
and bootstrap a fresh project with an empty Roc package cache. Use an
interactive Windows desktop for capture. Check focus, DPI, Narrator,
file dialogs, networking and workers. Install, start, upgrade and uninstall
the MSI on a clean machine. Cross-builds and Wine compatibility checks
provide separate evidence from native Windows runs. Hosted CI runs the
source checks on macOS, cross-builds on Linux, and checks the Win32
behavior scenarios on Windows x64. Run the interactive desktop
checks below for Narrator, input focus, and display settings.
The workflow's manual options run the external UI Automation probe and
native ARM64 scenarios when those runners are available. The `standalone`
option stages a local release preview on macOS and verifies a Reading List
project generated from that preview on Windows x64 with a fresh Roc cache.

Run xref:accessibility.adoc#verify-uia[the accessibility probe and desktop
walkthroughs] before recording accessibility verification for a release.

[#windows-handoff]
== Windows handoff checks

Use an interactive Windows desktop and record the OS build and the app
architecture with each result. Run the following with the bundled
targets from this checkout. Use `arm64mingw` for the native app tests on
Windows on Arm.

[source,powershell]
----
blueprint run test-native -- --target x64mingw
blueprint run test-accessibility -- -FreshStarter
----

Run the keyboard probes in `tests/native-keyboard/` and repeat the
Reading List accessibility check on a project created by the standalone
release launcher. In `windows.roc dev`, press Ctrl+R after a valid edit
and then after a syntax error. Verify that a valid edit starts a fresh
app instance and a failed build reopens the last successful executable.
Record cross-build, Wine, and native Windows results separately.

Track the remaining accessibility work in
https://github.com/lukewilliamboswell/roc-native-windows/issues/1[Native control accessibility]

[#windows-diagnostics]
== Diagnose a local Windows build

Use the example's `build/x64mingw/` or `build/arm64mingw/` executable from
the commit under test. Save traces and local tools under the ignored
repository-root `build/windows-diagnostics/` directory.

* For a UI Automation failure, open the example and use Live Inspect in
  https://accessibilityinsights.io/downloads/[Accessibility Insights for Windows].
  Inspect the control's name, relationships, patterns, and events around the
  failing action. Compare them with the out-of-process probe and the
  xref:accessibility.adoc#verify-uia[keyboard and Narrator walkthrough].
* For an automated accessibility scan, extract the portable CLI ZIP from
  the https://github.com/microsoft/axe-windows/releases/tag/v2.4.2[Axe.Windows
  release]. Open the example on the interactive desktop at the same privilege
  level as the scanner. From the repository root, run the following with the
  extracted CLI on `PATH` or use its full path. Replace `1234` with the app's PID.
+
[source,powershell]
----
New-Item -ItemType Directory -Force build/windows-diagnostics/axe-windows
AxeWindowsCLI.exe --processid 1234 --outputdirectory build/windows-diagnostics/axe-windows --alwayssavetestfile
----
+
Each scan checks the app's current UI Automation tree. Use the native probe and
desktop walkthrough for workflow transitions, keyboard focus, and Narrator
feedback. Open the `.a11ytest` report in Accessibility Insights for Windows
to inspect individual findings.
* For a slow or unresponsive app, use `wpr -profiles` to find a recording
  profile. From an elevated PowerShell, check `wpr -status`, then start a CPU
  recording with `wpr -start CPU -filemode`. Reproduce the action once and
  use `wpr -stop build/windows-diagnostics/workers.etl`. Open the trace in
  WPA and filter to the app's process. WPA is available through the
  https://learn.microsoft.com/en-us/windows-hardware/test/wpt/[Windows Performance Toolkit].
* For suspected Win32 heap, handle, or lock misuse, use the Windows SDK's
  https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/application-verifier-testing-applications[Application Verifier].
  Give a copy of the app a unique executable name, enable its Basics tests,
  and launch it under a debugger. Delete the settings for that name when
  finished with `appverif -delete settings -for workers-verifier.exe`.
* For image metadata and hashes, extract
  https://learn.microsoft.com/sysinternals/downloads/sigcheck[Sigcheck].
  From the repository root, run `sigcheck64 -a -h -r examples/workers/build/x64mingw/workers.exe`
  with the tool on `PATH`, or use its extracted path. Use `sigcheck64a` on
  Windows on Arm. Compare the SHA-256 with the executable being debugged.
* For file, registry, and DLL activity, extract
  https://learn.microsoft.com/sysinternals/downloads/procmon[Process Monitor].
  Stop capture while setting an include filter on the executable's process
  name. Start capture, reproduce the operation, then stop and save the events
  as a `.PML` file. Check the filtered trace before sharing it because paths
  and process details can contain local information.

[#review-host-authority]
== Review each feature's security model

Include a security discussion in every feature design or change
description. Use xref:architecture.adoc#capability-boundary[the authority
contract] and describe the feature's hazards, the controls that address
them, and what remains outside those controls. For work that leaves the
security boundary as it is, a brief explanation is enough.

* Name the user workflow, what the app author makes available, and
  what the user authorizes. Identify sensitive data and operations,
  who can supply their inputs, and what could go wrong. Consider
  untrusted data, dependencies, resource replacement, and exhaustion
  where relevant.
* Show the usual call with its safe defaults. For an unattended grant,
  explain why user designation and app-scoped facilities do not cover
  the workflow. State the target, allowed operations, who can receive
  the authority, its limits and lifetime, and when it is released.
  For a retained grant, describe revocation and what can reopen it.
* List the typed outcomes the caller can act on and explain any
  structured payload. Show how the caller handles denial or refusal
  without interpreting diagnostic text.
* Trace the controls through the actual host paths, including raw
  requests, simulation, redirects or file replacements, and
  cancellation where applicable. Verify that denial leaves the
  target untouched and consumes no in-flight slot. Check that
  read-only access stays read-only across the ABI and in workers.
* Exercise the ordinary path with its defaults and the failure paths
  that establish the controls. Verify desktop interactions on native
  Windows. Use specs for repeatable policy and result behavior.

Put lasting explanations of hazards, controls, and security limits
in the relevant manual chapter. Keep API doc comments focused on the
contract callers need at the call site, including authority, defaults,
and result tags. Link to the manual for the rationale and examples.

[#record-example-gallery]
== Refresh the README recordings

From an example's directory, record its gallery scenario on a Windows desktop.

[source,powershell]
----
roc ../../cli/windows.roc -- record tests/specs/demo.scm --format gif
----

The command prints its output directory under `build/specs/`. Copy the
resulting `demo.gif` to `docs/images/<example>.gif` at the repository root.
Keep the example's scenario under `tests/specs/` so the recording can be
repeated.

The HTTP demo uses a local response. Run this from `examples/http` in a
separate terminal while recording that example.

[source,powershell]
----
roc ../../scripts/serve.roc -- tests/fixtures --port 48393
----

[#build-the-platform]
== Cross-build the platform from source

For the maintainer build on Apple Silicon macOS, install Blueprint 0.13.0,
Roc as `roc`, Zig 0.17.1, and Rustup.
`Blueprint.roc` names the tooling compiler and `Blueprint.lock` carries
the fetched digests. `rust-toolchain.toml` selects the Rust version and
Windows targets. Use the Roc nightly validated by this checkout when
testing the current compiler and platform together.

[source,sh]
----
blueprint run check
blueprint run build
blueprint run bundle
blueprint run docs
----

`check` runs Rust format, lint, and portable tests, checks generated ABI
bindings using the vendored `host/glue/RustGlue.roc`, runs Roc expects and
spec validation, and cross-builds the examples. `build` writes the example executables under
`examples/<name>/build/<target>/`. `bundle` writes the Windows platform
bundle to `dist/platform/`. `docs` renders the manual website, Markdown,
and PDF under `.docs-out/` on macOS or Linux using the locked `roc-docs`
utility from roc-automation. The Documentation workflow builds the same
manual for pull requests and publishes the main branch to
https://lukewilliamboswell.github.io/roc-native-windows/[GitHub Pages].

The platform examples depend on the local platform through relative
paths. Keep compiler pins in `scripts/`, keep generated ABI changes
reviewable, and keep build products out of source control. An example
with specs adds `.scm` files under `tests/specs/` and data under
`tests/fixtures/`.

To exercise packaging directly from the checkout, build the local MSI
packager and run the CLI from the example directory.

[source,sh]
----
blueprint run packager
export ROC_WINDOWS_MSI="$PWD/packaging/target/release/roc-windows-msi"
cd examples/counter
roc ../../cli/windows.roc -- package --target x64mingw
----

[#stage-a-release]
== Stage a release

On Apple Silicon macOS, add the Intel macOS and Linux musl Rust targets
for the release packagers. Build the platform bundle and pass its
generated path, the release version and the public asset base URL.

[source,sh]
----
rustup target add x86_64-apple-darwin x86_64-unknown-linux-musl aarch64-unknown-linux-musl
blueprint run bundle
blueprint run release -- 0.0.1 dist/platform/HASH.tar.zst "$RELEASE_BASE_URL" dist/release
----

The output directory must be new. Every attachment includes the version.
The CLI and platform bundle use underscores in the version so Roc can
read URLs containing a dotted release tag. The standalone launcher,
the six packagers, and the two license files use the dotted version.
The scaffold writes the fetched launcher as `windows.roc`.

Stage and serve the files to test a local HTTP URL.

[source,sh]
----
blueprint run release -- --local 0.0.1 dist/platform/HASH.tar.zst dist/release-preview
blueprint run serve -- dist/release-preview
----

The preview server uses Basic CLI's TCP support and binds to
`127.0.0.1:8000`. If you choose a different port with `serve --port`,
pass the matching loopback URL to the release task when staging the files.

In another terminal, set `TOOL_BUNDLE` to the generated
`windows-0_0_1-HASH.tar.zst` filename and use a fresh directory and cache
to check the first-user path.

[source,sh]
----
roc "http://127.0.0.1:8000/$TOOL_BUNDLE" -- init /tmp/windows-release-preview
cd /tmp/windows-release-preview
roc windows.roc -- test --check
roc windows.roc -- package --target x64mingw
roc windows.roc -- package --target arm64mingw
----

On Linux, reuse the built platform archive and pass
`--packagers DIR` with the six macOS-stage packagers for the same version.
Before a public release, verify the exact bytes to be published, include
license and provenance evidence, and produce validated SBOM sidecars.
Use the https://github.com/lukewilliamboswell/roc-automation/blob/main/docs/platforms.adoc[roc-automation platform guide]
for the release matrix and the
https://github.com/lukewilliamboswell/roc-automation/blob/main/docs/software-bill-of-materials.adoc[SBOM contract]
for release evidence.
